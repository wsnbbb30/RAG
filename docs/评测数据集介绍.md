## 2. FinAR-Bench：中文 A 股年报表格问答

### 2.1 数据集简介

FinAR-Bench 是当前**最贴近 PaiSmart 项目目标**的外部基准数据集。它基于真实 A 股上市公司年报构建，每个样本包含一份完整的 Markdown 财务报表（利润表、资产负债表、现金流量表）和 13 道标注题目。题目分三类：事实提取（fact）、指标计算（indicator）、财务推理（reasoning）。

它与 PaiSmart 的核心关联在于：验证系统能否从年报表格中准确提取数值、计算财务指标、并基于多维度条件进行合规判断——这正是 PaiSmart 上市审核 RAG 场景的核心能力。

### 2.2 本地文件与规模

| 路径 | 实际内容 | 规模/备注 |
|---|---|---|
| `data/FinAR-Bench/dev.txt` | 开发集 JSONL | 10 行、10 公司、130 题，每公司 13 题 |
| `data/FinAR-Bench/test.txt` | 测试集 JSONL | 90 行、90 公司、1,170 题，每公司 13 题 |
| `pdf_data/pdf_data/` | 原始 A 股年报 PDF | 实际 101 个 PDF，约 72.39 MB |
| `pdf_extractor_result/.../txt_output/{tool}/` | 同批 PDF 的文本抽取结果 | `mineru`、`pdfminer`、`pdfplumber`、`pdftotext`、`pymupdf`、`pypdf` 各 100 个 TXT |

PDF 数量、开发/测试公司数和各解析器 TXT 数量并不完全相同。因此使用时不应假设"每个 JSON 样本都有同名 PDF 和每种解析结果"；应先按证券代码交集核对。

### 2.3 数据实例详解

#### 2.3.1 样本顶层结构

每行 JSON 包含三个顶层字段。以下以 dev 集第一条样本（鼎信通讯，603421.SH）为例：

```json
{
  "table": "# 利润表\n| 项目 | 2023年12月31日 | 2022年12月31日 |\n...\n# 资产负债表\n...\n# 现金流量表\n...",
  "instances": [ /* 13道题目，见下文 */ ],
  "file_path": "./data/pdf_data/603421.pdf"
}
```

`table` 字段是一份完整的 Markdown 格式财务报表，以 `# 利润表`、`# 资产负债表`、`# 现金流量表` 三个标题划分。表格首列为会计科目名称，其余列为各年度日期及金额（带千分位、正负号和小数）。例如利润表开头部分：

```
| 项目 | 2023年12月31日 | 2022年12月31日 |
|----|-------------|-------------|
| 营业总收入 | 3,632,703,199.78 | 3,114,981,021.66 |
| 营业收入 | 3,632,703,199.78 | 3,114,981,021.66 |
| 营业总成本 | 3,625,781,831.61 | 2,997,448,583.99 |
| 营业成本 | 2,155,518,926.03 | 1,745,733,139.74 |
| 销售费用 | 618,211,507.52 | 504,933,608.92 |
| 管理费用 | 203,400,886.94 | 199,227,549.79 |
| 财务费用 | 30,194,837.90 | 26,452,243.20 |
| 营业利润 | 148,434,554.03 | 113,408,511.36 |
| 利润总额 | 149,881,363.58 | 113,807,234.30 |
| 所得税 | 18,661,174.42 | -4,873,396.21 |
| 净利润 | 131,220,189.16 | 118,680,630.51 |
| 归属于母公司股东的净利润 | 131,220,189.16 | 118,680,630.51 |
| 基本每股收益 | 0.20 | 0.18 |
| 稀释每股收益 | 0.20 | 0.18 |
```

注意真实数据中的细节：
- 会计科目命名并不统一，"归属于母公司股东的净利润"不同于常见的"归母净利润"，且可能混用"帐/账""合计/净额"等变体
- 金额带千分位分隔符（如 `3,632,703,199.78`），解析时需去逗号
- 某些行可能是 `0.00` 表示不适用（如金融类科目在一般企业报表中留空）
- 存在 `-4,873,396.21` 这样的负值（如所得税为负数，代表递延所得税资产）

#### 2.3.2 三种任务类型与实例

每家公司 13 道题目，分为三类。dev 和 test 的题型分布如下：

| 切分 | 文档/公司 | fact | indicator | reasoning | 合计 |
|---|---:|---:|---:|---:|---:|
| dev | 10 | 60 | 60 | 10 | 130 |
| test | 90 | 540 | 540 | 90 | 1,170 |
| 合计 | 100 | 600 | 600 | 100 | 1,300 |

**类型一：fact（事实提取）**

从报表表格中直接提取指定科目的数值，无需计算。每道题可能要求提取 1 到多个科目。

实例 — 鼎信通讯（603421.SH）：

```json
{
  "task_id": "348fa9ddd50a4e2398b746208e908de7",
  "task": "提取公司合并财务报表中2022和2023的归属于母公司股东的净利润的数据。生成一个markdown格式的表格，表头为项目,2022,2023",
  "ground_truth": "| 项目 | 2022 | 2023 |\n|----|----|----|\n| 归属于母公司股东的净利润 | 118680630.51 | 131220189.16 |",
  "task_type": "fact",
  "task_num": 1,
  "company": "鼎信通讯",
  "company_code": "603421.SH"
}
```

再如一个要求提取 4 个科目的 fact 题（第二家公司，展鹏科技）：

```json
{
  "task": "提取公司合并财务报表中2022和2023的应收账款,营业成本,筹资活动产生的现金流量净额,固定资产净额的数据。生成一个markdown格式的表格，表头为项目,2022,2023",
  "ground_truth": "| 项目 | 2022 | 2023 |\n|----|----|----|\n| 应收账款 | 503715978.16 | 537739727.38 |\n| 营业成本 | 1767997706.72 | 2028720807.58 |\n| 筹资活动产生的现金流量净额 | -310811927.06 | 51199533.9 |\n| 固定资产净额 | 930727070.81 | 1141814050.05 |"
}
```

重点观察：
- GT 中的金额已去掉千分位分隔符（`118680630.51` 而非 `118,680,630.51`）
- 年序列从 "2022年12月31日/2023年12月31日" 简化为 "2022/2023"
- 科目名需与 `table` 中精确匹配（如 "归属于母公司股东的净利润" 而非 "归母净利润"）
- 多科目提取时，需同时准确定位每个科目

**类型二：indicator（指标计算）**

基于财务报表数据，按财务会计口径计算指标（如比率、增长率、周转天数等），结果通常要求保留指定小数位。

实例 — 鼎信通讯（603421.SH）：

```json
{
  "task_id": "b4ca590e90834e89898a203c46ac55d4",
  "task": "计算公式合并财务报表中2023的管理费用占营业总收入的比例的数据。生成一个markdown格式的表格，表头为项目,2023。比率表示为小数，保留4位小数",
  "ground_truth": "| 项目 | 2023 |\n|----|----|\n| 管理费用占营业总收入的比例 | 0.056 |",
  "task_type": "indicator",
  "task_num": 1,
  "company": "鼎信通讯",
  "company_code": "603421.SH"
}
```

验证计算：管理费用 ÷ 营业总收入 = 203,400,886.94 ÷ 3,632,703,199.78 ≈ 0.0560（四舍五入到 4 位小数）。

indicator 题的关键挑战：
- **会计口径正确性**：例如"资产负债率"需用"负债合计"除以"资产总计"，而非"流动负债"
- **平均存量处理**：周转率类指标通常要用（期初+期末）/2 计算平均值
- **公式和精度**：一道题可能要求 1、2、4、8、16 甚至 32 个指标，每个指标都有独立公式，且需精确到指定小数位
- **术语归一化**：`table` 中科目名可能是"营业总收入"而非"营业收入"，或"归属于母公司股东的净利润"而非"归母净利润"，计算前需正确映射

**类型三：reasoning（推理判断）**

根据数十个财务条件，判断公司财务状况是否符合各条件，并给出综合分析。

实例 — 鼎信通讯（603421.SH）：

```json
{
  "task": "根据给定的判断条件和公司的合并财务报表数据，完成以下任务: 1. 判断公司2023年的财务状况是否符合这些条件。生成一个markdown格式的表格，包含"条件序号"、"是否符合"两列。2. 根据第一步的结果，对成立的条件进行综合分析和总结",
  "ground_truth": "| 序号 | 是否符合 |\n|----|----|\n| 0 | 0 |\n| 1 | 0 |\n| 2 | 0 |\n| 3 | 1 |\n| 4 | 0 |\n...",
  "task_type": "reasoning",
  "conditions": "| 序号 | 条件 |\n|----|----|\n| 0 | 期间费用率增加 |\n| 1 | 权益乘数下降 |\n| 2 | 速动比率下降 |\n| 3 | 筹资活动产生的现金流量净额大于0 |\n| 4 | 净资产收益率下降 |\n..."
}
```

reasoning 题的 `conditions` 字段包含 64 条具体的财务判断条件，覆盖盈利能力、偿债能力、营运能力、现金流等维度。例如：
- "资产周转率增加" → 需计算两年的总资产周转率并比较
- "筹资活动产生的现金流量净额大于 0" → 直接从现金流量表取值判断
- "营业总收入增长率大于净利润增长率" → 需计算两个比率再比较

GT 中 0/1 表示不符合/符合。由于推理过程复杂且需要结构化解释，reasoning 题的自动评分难度远高于 fact 和 indicator。

### 2.4 JSONL 顶层结构总结

| 字段 | 类型 | 含义 |
|---|---|---|
| `table` | string | Markdown 格式完整财务报表，以 `# 利润表`、`# 资产负债表`、`# 现金流量表` 划分 |
| `instances` | array | 同一公司固定 13 道题，覆盖 fact/indicator/reasoning |
| `file_path` | string | 数据集声明的相对 PDF 路径，使用时应转换为本地路径 |

### 2.5 实例字段与任务结构

| 字段 | 类型 | 含义 |
|---|---|---|
| `task_id` | string | 题目唯一 ID |
| `task` | string | 中文自然语言任务，通常要求以 Markdown 表格输出 |
| `ground_truth` | string | GT 答案，通常是 Markdown 表格 |
| `task_type` | string | `fact`、`indicator` 或 `reasoning` |
| `task_num` | integer | 题目编号；同公司内递增 |
| `company` / `company_code` | string | 公司名及 A 股证券代码，如 `603421.SH` |
| `conditions` | string，可选 | reasoning 题专属，64 条财务判断条件表 |

### 2.6 与 PaiSmart 的匹配方式

FinAR-Bench 是当前最贴近项目目标的外部数据集，可形成三层验证：

1. **解析层**：用原始 PDF 与六种已有 TXT 输出对比 PaiSmart 的 PDF 页面、段落、表格与跨页处理；
2. **检索/事实层**：用 `table` 或解析结果构造 chunk，评估目标科目、年度和值的 Recall@K、MRR、数值 EM；
3. **计算/回答层**：用 `indicator` 的 GT 评估确定性计算，随后补齐 reasoning 的判断和解释评估。

仓库当前实际完成的是以 dev `table` 为上下文的 indicator 专项。该结果详见 `docs/FinAR-Bench财务指标计算评测报告.md`；它不是 101 份 PDF 的端到端解析成绩，也不是 test 集成绩。

## 3. FinQA：英文财务数值推理

### 3.1 数据集简介

FinQA 是面向**英文财务报告的数值推理**数据集，源自美国上市公司披露文档（年报、季报等）。它的核心特点是：每道题不仅提供答案，还提供了**可执行的计算程序（program）和原子步骤（steps）**，标注了每步操作（如 `divide`、`subtract`）及其操作数来源。这使得 FinQA 不仅能评估"答对了吗"，还能评估"计算逻辑对吗"。

与 FinAR-Bench 的区别：FinQA 是英文、美国 GAAP 口径、评测点是"从表格和文本中找到数字并按公式计算"，而不是中文 A 股场景。但它对 PaiSmart 验证操作数检索→程序执行的完整链路很有价值。

### 3.2 本地文件

| 文件 | 条目数 | 本地大小 | 用途 |
|---|---:|---:|---|
| `dataset/train.json` | 6,251 | ~78 MB | 训练集 |
| `dataset/dev.json` | 883 | ~11 MB | 验证集 |
| `dataset/test.json` | 1,147 | ~14 MB | 公开测试集，含参考信息 |
| `dataset/private_test.json` | 919 | ~5.6 MB | 私有测试集，README 说明不含参考信息 |

仓库同时保留了官方 retriever、generator 和 `code/evaluate/evaluate.py`。

### 3.3 数据实例详解

#### 3.3.1 顶层结构

每个样本包含三段上下文和一组问答。以 dev 集第一条样本（Visa 公司 2008 年报第 17 页）为例：

```
pre_text (44段)        → 表格之前的文本段落
post_text (21段)       → 表格之后的文本段落
table_ori (7行)        → 原始表格
qa                     → 问答 + 程序 + 证据标注
```

`pre_text` 和 `post_text` 是 PDF 页面中表格前后的叙述文本段落。例如 pre_text 中提及：

> "Based on payments volume, total volume, number of transactions and number of cards in circulation, Visa is the largest retail electronic payments network in the world."

而 `table_ori` 是这些文本中间嵌入的表格：

| Company | Payments Volume (billions) | Total Volume (billions) | Transactions (billions) | Cards (millions) |
|---|---|---|---|---|
| Visa Inc. | $2,457 | $3,822 | 50.3 | 1,592 |
| MasterCard | 1,697 | 2,276 | 27.0 | 916 |
| American Express | 637 | 647 | 5.0 | 86 |
| ... | ... | ... | ... | ... |

#### 3.3.2 QA 结构与程序

FinQA 每个样本的 `qa` 是核心，包含问题、答案、程序、步骤和证据标注：

| 字段 | 含义 |
|---|---|
| `question` / `answer` | 问题及规范答案 |
| `ann_table_rows` / `ann_text_rows` | 人工标注的表格行/文本行证据索引 |
| `steps` | 原子运算步骤，允许中间变量引用（如 `#0`, `#1`） |
| `program` | 如 `divide(637, const_5)` 的可执行表达式 |
| `gold_inds` | 金证据索引 |
| `exe_ans` | 程序执行答案 |

#### 3.3.3 简单示例：单步除法

问题：**"What is the average payment volume per transaction for American Express?"**

```json
{
  "question": "what is the average payment volume per transaction for american express?",
  "answer": "127.40",
  "program": "divide(637, const_5)",
  "steps": [
    {
      "op": "divide1-1",
      "arg1": "637",
      "arg2": "const_5",
      "res": "127.40"
    }
  ],
  "ann_table_rows": [3],
  "ann_text_rows": []
}
```

解读：从表格第 3 行（American Express 行）取 Payments Volume = 637（十亿）和 Transactions = 5.0（十亿），637 ÷ 5.0 = 127.40（每笔交易平均金额）。操作数 `637` 和 `const_5` 分别对应表格中两个单元格的值。

#### 3.3.4 复杂示例：四步推理

问题：**"In 2010 what was the percentage change of the carrying amount of loan receivable net of the allowance?"**

```json
{
  "question": "in 2010 what was the percentage change of the carrying amount of loan receivable net of the allowance",
  "answer": "-52.5%",
  "program": "subtract(920, 95), subtract(469, 77), subtract(#1, #0), divide(#2, #0)",
  "steps": [
    { "op": "minus2-1", "arg1": "920", "arg2": "95",   "res": "825" },
    { "op": "minus2-2", "arg1": "469", "arg2": "77",   "res": "392" },
    { "op": "minus2-3", "arg1": "#1",  "arg2": "#0",   "res": "-433" },
    { "op": "divide2-4","arg1": "#2",  "arg2": "#0",   "res": "-52.5%" }
  ],
  "ann_table_rows": [1, 8],
  "ann_text_rows": []
}
```

解读（还原财报语境）：
1. **Step 1**：当前年度贷款总额 920 - 拨备 95 = 账面净值 825（对应 `#0`）
2. **Step 2**：上年度贷款总额 469 - 拨备 77 = 账面净值 392（对应 `#1`）
3. **Step 3**：`#1` - `#0` = -433 → 净值变化额（负数=减少）
4. **Step 4**：`#2` ÷ `#0` = -52.5% → 变化百分比

这个例子展示了 FinQA 的核心价值：不仅验证"算对了 -52.5%"，还验证四步推理中每一步的操作数和操作是否正确。对 PaiSmart 而言，这意味着可以诊断"是提取错了操作数，还是公式用错了，还是精度/单位问题"。

### 3.4 与 PaiSmart 的适配方式

先统计 `steps/program` 中的操作与最大深度，再与 `FormulaRegistry` 做覆盖映射；随后仅选取约 50 条单步或两步、单位规则清晰的题目，以双语或保留英文证据的方式做受控实验。建议分别记录：操作数 Recall@10、程序等价性、执行准确率、单位/舍入一致性。当前这些均为计划，未产生 PaiSmart 评测分数。

## 4. TAT-QA：表格与文本混合财务问答

### 4.1 数据集简介

TAT-QA（Table-And-Text Question Answering）是一个**混合表格与文本的财务问答**数据集。与 FinAR-Bench（纯表格）和 FinQA（以表格为主）不同，TAT-QA 的问题可能同时依赖表格数据和文本段落来回答。这对验证 PaiSmart 的**混合证据召回**能力特别有价值——上市审核场景中，所需的证据信息可能同时出现在年报的表格（如财务报表数据）和文本（如管理层讨论）中。

### 4.2 本地原始切分

| 文件 | 文档数 | 问题数 | 说明 |
|---|---:|---:|---|
| `dataset_raw/tatqa_dataset_train.json` | 2,201 | 13,215 | 训练原始数据 |
| `dataset_raw/tatqa_dataset_dev.json` | 278 | 1,668 | 开发/验证数据 |
| `dataset_raw/tatqa_dataset_test.json` | 278 | 1,669 | 测试问题数据 |
| `dataset_raw/tatqa_dataset_test_gold.json` | 277 | 1,663 | 测试 gold 数据 |

`dataset_tagop/` 和 `tag_op/` 是 TagOp 模型的预处理、训练与推断支持文件。官方 README 说明数据集总计 16,552 个问题、2,757 个混合上下文，使用 CC BY 4.0 许可。

### 4.3 数据实例详解

#### 4.3.1 文档结构

每份文档有 `table`、`paragraphs`、`questions` 三个顶层字段。以 dev 集第一个文档为例：

**表格** — 一家工程公司的收入按合同类型划分：

| | | Years Ended September 30, | |
|---|---|---|---|
| | 2019 | 2018 | 2017 |
| Fixed Price | $1,452.4 | $1,146.2 | $1,036.9 |
| Other | 44.1 | 56.7 | 70.8 |
| Total sales | $1,496.5 | $1,202.9 | $1,107.7 |

**段落 1** — 解释合同类型：

> "Sales by Contract Type: Substantially all of our contracts are fixed-price type contracts. Sales included in Other contract types represent cost plus and time and material type contracts."

**段落 2** — 解释各合同类型的结算方式：

> "On a fixed-price type contract, we agree to perform the contractual statement of work for a predetermined sales price. On a cost-plus type contract, we are paid our allowable incurred costs plus a profit which can be fixed or variable depending on the contract's fee arrangement... On a time-and-material type contract, we are paid on the basis of direct labor hours expended at specified fixed-price hourly rates..."

#### 4.3.2 题目类型与实例

该文档包含 6 道题，覆盖了 span（抽取）、multi-span（多片段）、arithmetic（算术）三种题型和 text（文本）、table-text（表格+文本）两种证据来源：

**题 1 — span / 纯文本**

```json
{
  "question": "What is the company paid on a cost-plus type contract?",
  "answer": ["our allowable incurred costs plus a profit which can be fixed or variable depending on the contract's fee arrangement up to predetermined funding levels determined by the customer"],
  "answer_type": "span",
  "answer_from": "text",
  "rel_paragraphs": ["2"],
  "req_comparison": false
}
```

→ 答案直接来自段落 2 的原文摘录，无需计算，也无需查表。

**题 2 — span / 表格+文本**

```json
{
  "question": "What is the amount of total sales in 2019?",
  "answer": ["$1,496.5"],
  "answer_type": "span",
  "answer_from": "table-text",
  "rel_paragraphs": ["2"],
  "scale": "million"
}
```

→ 答案来自表格的 "Total sales" 行、"2019" 列。但段落 2 提供了上下文（"The table below presents total net sales..."），所以证据来源标为 `table-text`。

**题 3 — multi-span / 纯文本**

```json
{
  "question": "What are the contract types?",
  "answer": ["fixed-price type", "cost-plus type", "time-and-material type"],
  "answer_type": "multi-span",
  "answer_from": "text",
  "rel_paragraphs": ["1", "2"]
}
```

→ 答案分散在两个段落中，需要从多处文本中提取并合并。

**题 4 — span + 比较**

```json
{
  "question": "In which year is the amount of total sales the largest?",
  "answer": ["2019"],
  "derivation": "1,496.5 > 1,202.9 > 1,107.7",
  "answer_type": "span",
  "answer_from": "table-text",
  "req_comparison": true,
  "scale": ""
}
```

→ 需要先读取表格中三年的 Total sales 值，再比较大小，最后输出最大年份。注意 `req_comparison: true` 标记了"需要比较"。

**题 5 — arithmetic / 表格+文本**

```json
{
  "question": "What is the change in Other in 2019 from 2018?",
  "answer": -12.6,
  "derivation": "44.1 - 56.7",
  "answer_type": "arithmetic",
  "answer_from": "table-text",
  "scale": "million"
}
```

→ 需要从表格中取 2019 年 Other = 44.1 和 2018 年 Other = 56.7，相减得 -12.6（百万）。

**题 6 — arithmetic / 表格+文本，百分比变化**

```json
{
  "question": "What is the percentage change in Other in 2019 from 2018?",
  "answer": -22.22,
  "derivation": "(44.1 - 56.7) / 56.7",
  "answer_type": "arithmetic",
  "answer_from": "table-text",
  "scale": "percent"
}
```

→ 同样的操作数，乘以不同的公式，得出百分比变化约 -22.22%。

#### 4.3.3 整体题型分布

对 dev 集 1,668 题的实测分布：

| 维度 | 分类 | 数量 |
|---|---|---|
| 按 `answer_type` | arithmetic | 718 |
| | span | 701 |
| | multi-span | 217 |
| | count | 32 |
| 按 `answer_from` | table | 772 |
| | table-text | 507 |
| | text | 389 |

数据说明：约 43% 的题目需要算术计算，约 77% 的题目至少涉及表格数据（pure table + table-text），约 30% 需要同时理解文本和表格。

### 4.4 题目字段说明

| 字段 | 含义 |
|---|---|
| `uid` / `order` | 题目 ID 与顺序 |
| `question` / `answer` | 问题与答案 |
| `derivation` | 算术推导/公式文本 |
| `answer_type` | `span`、`multi-span`、`arithmetic`、`count` |
| `answer_from` | `text`、`table`、`table-text` |
| `rel_paragraphs` | 相关段落标识 |
| `req_comparison` / `scale` | 是否需要比较与量纲信息 |

### 4.5 与 PaiSmart 的适配方式

TAT-QA 的强项是可验证混合证据召回。建议先把文本段落作为 gold chunk，测试 BM25、Vector 及 RRF 的 Text Recall@10/MRR；再选择少量 `table` 和 `table-text` 题，建立与 PaiSmart `FinancialFact`/表格单元格的映射。英文数据和非 A 股口径会影响 embedding 与指标字典匹配，因此当前更适合作为检索机制验证，不宜直接对外声称金融业务端到端得分。

## 5. PaiSmart 实验输出：eval-results

### 5.1 数据集简介

`data/eval-results/` 是 PaiSmart 在 FinAR-Bench 上运行评测的**实际实验输出**，共 35 个 JSON 文件。每个文件记录了一次完整评测运行的快照，包含该次运行的检索效果、指标计算准确率和具体 bad case 详情。这些文件可以直接用来分析 PaiSmart 当前在 FinAR-Bench 上的表现和瓶颈。

注意：其中有 8 个文件（`finarbench-eval-14e45b80.json`、`finarbench-eval-635ae162.json` 等）仅有 41 字节，是初始化失败或空运行的占位文件，不能当作有效评测结果。

### 5.2 有效评测结果结构

一个完整的评测结果 JSON 包含以下字段，以 `finarbench-eval-0db872a9.json`（runId: 0db872a9，130 道题的首次批量运行）为例：

```json
{
  "runId": "0db872a9",
  "timestamp": 1785315425.7905154,
  "totalCases": 130,
  "passedCases": 0,
  "skippedCases": 10,
  "avgRecallAt5": 0.0,
  "avgRecallAt10": 0.0,
  "avgMrr": 0.0,
  "stockCodeExtractionAccuracy": 0.0,
  "yearExtractionAccuracy": 0.4615,
  "metricsByType": {
    "fact":      { "total": 60, "passed": 0, "skipped": 0, "avgRecall": 0.0, "avgMrr": 0.0 },
    "indicator": { "total": 60, "passed": 0, "skipped": 0, "avgRecall": 0.0, "avgMrr": 0.0 },
    "reasoning": { "total": 10, "passed": 0, "skipped": 10, "avgRecall": 0.0, "avgMrr": 0.0 }
  },
  "badCases": [ /* 130个失败case的详情 */ ]
}
```

关键发现：
- `passedCases: 0` → 全部 130 题无通过，Recall 和 MRR 均为 0，说明此阶段处于基线归零状态
- `yearExtractionAccuracy: 46.15%` → 年度提取有 46% 正确，说明"找到哪一年的数据"有一定能力
- `stockCodeExtractionAccuracy: 0.0` → 证券代码提取完全失败，可能是检索排序阶段未匹配
- reasoning 的 10 题全部跳过，因为未接入 reasoning 自动评分

### 5.3 Bad Case 示例

每个 bad case 记录了一道题目的失败详情。以下为三个典型 fact 类型的 bad case：

**Case 1 — 单科目提取失败**

```json
{
  "taskId": "348fa9ddd50a4e2398b746208e908de7",
  "taskType": "fact",
  "question": "提取公司合并财务报表中2022和2023的归属于母公司股东的净利润的数据。生成一个markdown格式的表格，表头为项目,2022,2023",
  "expectedSummary": "1 facts expected",
  "retrievedSummary": "found 0",
  "reason": "found 0/1 facts in candidates"
}
```

→ 需要从候选 chunk 中找到一个事实（归属于母公司股东的净利润，两年数据），但检索结果中完全找不到。

**Case 2 — 双科目提取失败**

```json
{
  "taskId": "c2901f8f116842e1b4f074c65a126665",
  "taskType": "fact",
  "question": "提取公司合并财务报表中2022和2023的应付债券,应收账款的数据。生成一个markdown格式的表格，表头为项目,2022,2023",
  "expectedSummary": "2 facts expected",
  "retrievedSummary": "found 0",
  "reason": "found 0/2 facts in candidates"
}
```

→ 需要两个科目（应付债券 + 应收账款），但均未在候选中找到。

**Case 3 — 四科目提取（全失败）**

```json
{
  "taskId": "5b9899ec39fc4e4c9553c1ccf78e8509",
  "taskType": "fact",
  "question": "提取公司合并财务报表中2022和2023的归属于母公司所有者权益合计,应付职工薪酬,营业利润,筹资活动产生的现金流量净额的数据。生成一个markdown格式的表格，表头为项目,2022,2023",
  "expectedSummary": "4 facts expected",
  "retrievedSummary": "found 0",
  "reason": "found 0/4 facts in candidates"
}
```

→ 四科目全缺，表明检索阶段对表格嵌入的向量召回完全未能匹配到目标科目。

这些 bad case 共同指向的问题：在当前运行配置下，检索阶段无法从 chunk 中找到与 GT 科目名匹配的内容。可能原因包括：科目名称未归一化（如 GT 用"归属于母公司股东的净利润"而索引用"归母净利润"）、embedding 对表格数值不敏感、chunk 切分破坏了表格结构等。

### 5.4 使用注意事项

实验结果必须连同代码版本、ES 索引状态、Embedding/LLM 配置、topK、是否启用确定性计算和数据切分一起解释。历史 JSON 中的检索运行结果与最终 indicator 专项报告的 630 个子指标计算结果属于不同口径，不能直接拼接。

## 6. 数据集使用与治理建议

1. 原始外部数据、转换脚本、评测配置和运行输出分目录保存；对外仓库应先检查许可证与原始数据再分发限制。
2. 建立样本映射表：证券代码/文件名、PDF、解析产物、Markdown 表、文档版本、ES 索引 ID 与评测题 ID 应可互相追踪。
3. 每次切块、解析、检索、重排或计算逻辑变更后，分层回归，而不是只观察最终答案。
4. 对所有数值指标记录分母和口径：题目数、子指标数、跳过样本数、容差、候选 TopK 及是否使用 GT Markdown。
5. FinAR-Bench 是当前中文主基准；FinQA/TAT-QA 应报告为跨语言/跨市场方法验证，不能与主基准合并得分。
